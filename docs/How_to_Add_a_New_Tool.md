h# How to Add a New Tool to Insight-Arc

This guide explains how to add new tools to the Insight-Arc execution engine. It documents the exact current architecture—how tools are registered, executed, and exposed to the LLM—so you can confidently extend the application's capabilities.

## 1. The Complete Lifecycle of a Tool

1. **User Request**: The user submits a prompt, which enters `run_chat` in `intelligence/chatbot.py`.
2. **LLM Tool Selection**: `chatbot.py` packages the prompt, dataset metadata, analysis memory, and a list of available tool JSON schemas (generated by `get_llm_tools()`) and sends them to the hosted LLM.
3. **Tool Definition/Schema**: The LLM decides to use a tool and returns a `tool_calls` payload. `chatbot.py` extracts the tool name and JSON arguments.
4. **Executor**: `chatbot.py` calls `execute_tool()` in `intelligence/executor.py`, passing the arguments, `current_df`, and `last_result`.
5. **Python Function**: The executor fetches the `ToolDefinition` from `tool_definitions.py`. It uses the defined Pydantic schema to validate the arguments. It resolves the `source` argument to pick either `current_df` or `previous_result`. It then enforces any `max_input_rows` limits and executes the underlying Python function.
6. **Observation**: 
   - If the tool is a matplotlib visualization, `executor.py` automatically captures the figure to a base64 PNG.
   - If a non-modifying tool returns a `pd.DataFrame` or `pd.Series`, the executor saves it as `derived_result`.
   - `chatbot.py` passes the result to `build_observation()`, which generates a compact, character-budgeted text summary (like a miniature CSV) to avoid flooding the LLM context.
7. **LLM**: The compact text observation is appended to the conversation history, and the LLM is queried again.
8. **Final Response**: Once all tools succeed and the LLM has enough information, it returns a final textual answer without `tool_calls`. `chatbot.py` packages this alongside any generated charts and returns it to the user.

---

## 2. The Role of Each File

- **`intelligence/schemas.py`**: Defines Pydantic `BaseModel` classes representing the exact inputs a tool requires. These are automatically converted into the JSON schemas the LLM reads.
- **`intelligence/tools.py`** (and `modify.py`, `analysis/*.py`, `data/*.py`): Contains the actual standalone Python functions that execute business logic. Every tool function takes a pandas `DataFrame` as its first positional argument.
- **`intelligence/tool_definitions.py`**: The central registry. It exports a `TOOLS` dictionary mapping a string name to a `ToolDefinition` object, linking the Python function, its Pydantic schema, and configuration flags (`modifies_dataset`, `accepts_previous_result`, `max_input_rows`).
- **`intelligence/executor.py`**: The execution engine. It intercepts the execution, resolves the `source` argument, validates parameters via Pydantic schemas, safely captures global `matplotlib` figures, and returns a standardized execution dictionary back to the chat loop.
- **`intelligence/chatbot.py`**: The LLM orchestrator. Runs the ReAct loop, calls the LLM provider, manages `current_df` and `last_result` state, formats tool observations, and handles state clearing.

---

## 3. Can a Tool be Added Using ONLY These Files?

If you only modify `tools.py`, `modify.py`, `tool_definitions.py`, and `schemas.py`, what can you build?

**A. Tools that can be added using ONLY those files:**
- Any basic analytical tool (e.g., calculating a new statistical variance).
- Any standard dataset-modifying tool (e.g., normalizing a column).
- Any transformation tool that returns a DataFrame or Series.
*Reasoning: The architecture allows any standard pandas operation to be routed and executed seamlessly through these four files.*

**B. Tools that require changes elsewhere:**
- **Visualizations**: While you technically *could* place matplotlib code in `tools.py`, architectural conventions dictate they belong in `analysis/visualization.py`. No changes are required in the executor itself, but a new file is touched.
- **Domain-specific data processing**: Should be placed in `analysis/statistics.py` or `data/cleaner.py`.

**C. Tools that require new supporting modules/files:**
- **Non-Matplotlib Visualizations (e.g., Plotly, Altair)**: `executor.py` is hardcoded to capture `matplotlib.pyplot.gcf()`. Returning a Plotly HTML object would require modifying `executor.py` to recognize and serialize alternative visualization formats.
- **Tools requiring external API secrets**: Would require modifying the `.env` pipeline in `chatbot.py` or `main.py` to safely inject new credentials.

## 4. Step-by-Step Example: Adding a completely new tool

Let's add a tool that calculates the variance of a specific column.

**Step 1: Pydantic Input Schema (`schemas.py`)**
```python
class CalculateVarianceRequest(BaseModel):
    column: str = Field(..., description="Exact name of the numerical column.")
```

**Step 2: Python Implementation (`tools.py`)**
```python
def calculate_variance(df: pd.DataFrame, column: str) -> float:
    """Calculate the variance of a numerical column."""
    if column not in df.columns:
        raise ValueError(f"Column '{column}' does not exist.")
    return df[column].var()
```

**Step 3: ToolDefinition Registration (`tool_definitions.py`)**
```python
"calculate_variance": ToolDefinition(
    name="calculate_variance",
    description="Calculate the statistical variance of a numerical column.",
    function=tools.calculate_variance,
    input_schema=CalculateVarianceRequest,
    modifies_dataset=False,
    accepts_previous_result=True, # Allow running on a filtered/grouped subset
),
```

**How it works seamlessly:**
- **LLM Schema**: The LLM will automatically see `calculate_variance` with arguments `column` and `source` (injected because `accepts_previous_result=True`).
- **Executor**: If the LLM requests `source="previous_result"`, `executor.py` automatically routes the `last_result` DataFrame into `df` without the Python function needing to know.
- **Observation**: The executor returns the float, and `build_observation()` converts it into compact text for the LLM.

## 5. Configuring Different Types of Tools

- **Read-only analysis**: Set `modifies_dataset=False`. The tool should return a scalar or string.
- **Transformation/Derived-result**: Set `modifies_dataset=False`. Return a `pd.DataFrame` or `pd.Series`. The executor will automatically detect this and save it as `derived_result`, making it available as `last_result` for the next tool.
- **Dataset-modifying**: Set `modifies_dataset=True`. The tool **must** return the modified `pd.DataFrame`.
- **Visualization**: Implement using `matplotlib.pyplot`. Do not call `plt.show()`. The tool can return `None`. `executor.py` will automatically capture the active figure.
- **Consuming `last_result`**: Set `accepts_previous_result=True`. `executor.py` automatically injects a `source` enum (`"dataset"`, `"previous_result"`) into the JSON schema and routes the correct DataFrame to your function.

---

## 6. Current Architectural Rules

- **`current_df`**: The active, user-facing dataset. Mutated **only** if a tool succeeds with `modifies_dataset=True`.
- **`last_result`**: The most recent `pd.DataFrame` or `pd.Series` output by a non-modifying tool.
- **`source="dataset"`**: The tool executes against `current_df`. This is the strict default.
- **`source="previous_result"`**: The tool executes against `last_result`.
- **Clearing stale state**: If a modifying tool succeeds, `chatbot.py` instantly clears `last_result` to `None`. This prevents downstream tools from operating on a stale snapshot of the data.
- **Observation serialization**: Large DataFrames are never dumped entirely into the LLM context. `build_observation()` converts them into a compact CSV text block heavily truncated to `MAX_OBSERVATION_CHARS`. 
- **Plotting safety**: Expensive tools should declare a `max_input_rows` limit in their `ToolDefinition` (e.g., `MAX_BAR_CHART_ROWS = 1000`). `executor.py` validates this before the function even runs, immediately throwing a safe error back to the LLM if breached.
- **Errors**: Pydantic `ValidationError`s or Python exceptions raised by the tool are safely caught by `chatbot.py` and returned to the LLM as a `status: error` observation, allowing the agent to self-correct.

---

## 7. How the LLM Discovers the Tool

Discovery is purely static and deterministic. You do not need to prompt the LLM directly.
In `intelligence/chatbot.py`, the function `get_llm_tools()` iterates directly over the `TOOLS` dictionary imported from `tool_definitions.py`. 

For each `ToolDefinition`, it calls `get_json_schema()`. This method takes the Pydantic `BaseModel.model_json_schema()`, recursively strips out redundant metadata (like `title`), and dynamically injects the `source` parameter if `accepts_previous_result` is True. The resulting array of JSON objects is passed directly to the provider (e.g., DeepInfra) as the `tools` payload in the API request.

---

## 8. Tool Development Checklist

Before submitting a new tool, ensure you have:
- [ ] Defined an explicit Pydantic `BaseModel` for inputs in `schemas.py`.
- [ ] Written the Python function, ensuring `df: pd.DataFrame` is the first parameter.
- [ ] Registered the tool in `tool_definitions.py` within the `TOOLS` dictionary.
- [ ] Set `modifies_dataset=True` ONLY if the function returns an altered core dataset.
- [ ] Set `accepts_previous_result=True` if the tool makes sense to run against intermediate derived data (like a filtered subset).
- [ ] Set `max_input_rows = N` if the operation cost scales linearly per row (e.g., drawing individual scatter points).

---

## 9. Architectural Coupling

The current implementation is highly effective but possesses some architectural coupling that prevents "true" dynamic plug-and-play:
1. **Centralized Registry**: Tools cannot dynamically register themselves via decorators. They must be manually imported and hardcoded into the `TOOLS` dictionary in `tool_definitions.py`.
2. **Matplotlib Exclusivity**: `executor.py` is tightly coupled to `matplotlib`. It relies on inspecting `plt.get_fignums()` globally. To support a different plotting library, the core executor's `_capture_figure_png()` logic must be rewritten.
3. **Pandas Exclusivity**: The engine expects `derived_result` caching to only apply to `pd.DataFrame` or `pd.Series`.

---

## 10. Final Verdict

**"Can Insight-Arc currently support adding most tools without modifying the executor/LLM architecture?"**

**Yes.** Insight-Arc currently supports adding the vast majority of analytical, data-transformation, modifying, and matplotlib-based visualization tools strictly by defining the function, creating its Pydantic schema, and registering it in `tool_definitions.py`. The executor and LLM orchestrator safely handle routing, schema validation, plotting captures, and text truncation without any required changes to the core architecture.
